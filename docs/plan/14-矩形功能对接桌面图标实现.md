# 矩形功能对接桌面图标实现
## 目标

当前项目里的“矩形分组”本质上还是建立在 Windows 原生桌面图标之上：

- 矩形负责绘制背景和分组边界
- 图标仍然是 Explorer 的 `SysListView32` 在管理和绘制
- 应用只是读取图标坐标、改写图标坐标、在矩形内重新排布

这条路线能较快做出第一版，但天花板很明显：

- 图标始终受 Windows 桌面原生行为约束
- 右键、拖拽、自动排列、刷新、Explorer 重启都会影响分组体验
- 矩形永远只是“套在图标外面”，不是真正“托举图标”
- 想要做稳定的多分组、跨重启恢复、自由布局、拖拽缩放联动，复杂度会越来越高

本方案的目标，是把“矩形分组”升级为真正的图标承载容器：

- 矩形不再只是背景，而是图标的宿主区域
- 图标不再依赖 Windows 桌面自己的布局来呈现分组
- 应用自己负责图标的显示、命中、拖拽、排序、持久化和恢复
- Windows 桌面退化为“图标来源”和“系统能力提供者”，而不再是最终界面

一句话定义目标：

`矩形 = 我们自己的桌面图标容器，而不是 Windows 桌面上的高亮框`

## 目标完成后的用户体验

完成后，用户看到的应当是这样一条闭环：

1. 用户在桌面空白处拖出一个矩形。
2. 用户选择一批图标放入这个矩形。
3. 图标直接显示在矩形内部，由本应用负责布局与渲染。
4. 用户拖动矩形，矩形内图标跟随整体移动。
5. 用户拖动图标，图标在矩形内部改变顺序或位置。
6. 用户拉伸矩形，矩形内部自动重新排布图标。
7. 用户右键图标，出现和桌面一致或近似一致的操作菜单。
8. 用户双击图标，可正常打开文件、快捷方式、目录或应用。
9. 退出应用后，可以选择：
   - 恢复为 Windows 原生桌面图标布局
   - 或保留托管状态，等待下次应用启动继续接管
10. 再次启动应用后，所有矩形和矩形内图标恢复为上次托管状态。

这里的关键不是“看起来像分组”，而是：

- 图标的呈现归我们
- 图标的布局归我们
- 图标与矩形的关系归我们

## 先定义“真正不依赖 Windows 桌面”是什么意思

这里需要先统一定义，否则实现过程中很容易做成“半托管”。

### 不算真正脱离依赖的方案

以下都不算最终目标：

- 只是在桌面上画矩形背景，图标仍是 Explorer 画
- 继续通过 `LVM_SETITEMPOSITION` 把桌面图标塞进矩形
- 通过 `WorkerW` / `Progman` / `SetParent` 调层级，让矩形看起来在图标下方
- 继续依赖桌面图标命中、右键、拖拽、自动排列来完成分组交互

这些方案都只是“借用 Windows 桌面”，不是真正接管。

### 真正目标方案的判定标准

满足以下条件，才算真正完成：

1. 应用自己决定图标是否显示、显示在哪、如何排列。
2. 应用自己维护图标与矩形之间的从属关系。
3. 图标在矩形内的拖拽、重排、选中、命中，不依赖 `SysListView32`。
4. 即使 Windows 桌面图标隐藏，矩形内图标仍然完整可用。
5. Explorer 重启后，只要应用还在，矩形和图标仍能恢复。

## 推荐总方案

推荐采用：

`Windows 原生桌面图标作为数据源 + 应用自绘图标层作为真正显示层`

也就是双层结构：

### 第一层：系统桌面源层

由 Explorer 的桌面 ListView 提供：

- 初始图标清单
- 文件路径 / PIDL / 名称 / 类型
- 系统图标资源
- Shell 操作能力

这一层不再承担最终显示职责，只作为系统能力来源。

### 第二层：应用托管显示层

由本应用创建自己的“桌面图标承载层”，负责：

- 矩形绘制
- 图标绘制
- 图标命中测试
- 图标拖拽移动
- 图标排序与布局
- 选中态
- 右键菜单入口
- 双击打开
- 多矩形管理
- 数据持久化

用户最终看到并操作的，是第二层。

## 架构设计

建议把当前架构从“桌面读写工具”升级成“桌面托管运行时”。

### 一、运行时分层

建议增加以下模块：

#### 1. DesktopSourceService

职责：

- 连接 Explorer 桌面
- 枚举原生桌面图标
- 读取名称、路径、位置、系统图标
- 响应桌面刷新、Explorer 重启

这是“数据采集层”。

#### 2. ManagedDesktopRuntime

职责：

- 维护当前全部矩形分组
- 维护全部托管图标的运行时状态
- 提供矩形与图标之间的关系映射
- 处理启动恢复、退出恢复、异常恢复

这是整个方案的核心状态机。

#### 3. ManagedDesktopWindow

职责：

- 创建真正承载图标的桌面级窗口
- 负责自绘矩形和矩形内图标
- 提供命中测试、悬停、拖拽、选择框等交互

这是最终 UI 承载面。

#### 4. IconLayoutEngine

职责：

- 计算矩形内图标布局
- 支持网格、自由布局、吸附布局
- 处理矩形缩放后的重排
- 处理图标碰撞与越界

这是布局引擎。

#### 5. ShellActionBridge

职责：

- 双击打开
- 调系统右键菜单
- 重命名文件
- 删除、复制、剪切、属性
- 拖放目标解析

这是“图标看起来像桌面图标”的关键桥梁。

#### 6. PersistenceRuntimeStore

职责：

- 保存矩形
- 保存托管图标
- 保存图标在矩形内的位置和顺序
- 保存启动恢复策略
- 保存退出恢复策略

这是运行时数据闭环。

## 关键设计决策

### 决策一：图标显示必须切换到“自绘”

这是最重要的一条。

只有自己绘制图标，才可能真正做到：

- 图标视觉在矩形上层
- 不被桌面原生右键/选中逻辑打断
- 拖拽和重排逻辑完全可控
- 后续做动画、分页、折叠、缩略图、标签都可扩展

如果仍由 Windows 桌面自己画图标，那本方案从一开始就不是闭环。

### 决策二：Windows 原生桌面图标需要进入“隐藏或脱离展示”状态

当某个图标被应用托管后，用户不应同时看到：

- Windows 桌面上的原生图标
- 应用矩形内的托管图标

否则会出现双份图标。

建议采用两阶段策略：

#### 第一阶段：位置迁移隐藏

先把被托管图标移动到屏幕外保留区，或者桌面不可见区。

优点：

- 实现快
- 兼容已有 `MoveDesktopIcons`

缺点：

- 本质仍依赖 Explorer 图标存在
- 多屏和分辨率变更时容易出边界问题

#### 第二阶段：桌面显示整体隐藏 + 应用完全接管

最终目标应是：

- Windows 桌面图标整体隐藏
- 应用托管层独立显示全部被管理图标

未被托管的图标有两种方案：

1. 也进入应用托管层中的“未分组区域”
2. 暂时保留系统桌面显示，只对托管图标做隐藏

从产品完整度看，长期推荐第 1 种。

### 决策三：矩形窗口与图标窗口要解耦

不要再尝试一个全屏透明窗口同时承担：

- 背景绘制
- 鼠标交互
- 图标承载
- 右键桥接
- 桌面层级控制

更稳的方式是分层：

#### 展示层

- 负责矩形背景
- 负责静态视觉
- 永久 click-through

#### 交互层

- 只在编辑态出现
- 命中范围很小
- 负责矩形拖动、缩放、关闭、标题栏交互

#### 图标承载层

- 负责绘制矩形内部图标
- 负责图标命中、拖拽、右键、双击

这样能显著降低“影响其他窗口点击”“任务栏右键异常”“桌面全局右键串位”等问题。

## 真正托举图标的实现闭环

下面给出建议的完整闭环。

### 阶段 A：建立自绘图标层，但先不隐藏系统图标

目标：

- 在应用窗口中把图标画出来
- 实现双击打开和右键菜单
- 实现图标在矩形内的命中与拖拽

做法：

1. 新建 `ManagedDesktopWindow`
2. 每个矩形内根据 `ManagedIconInstance` 绘制图标和标题
3. 图标位图通过系统 SHGetFileInfo / IShellItemImageFactory 获取
4. 双击通过 ShellExecute / PIDL 调用打开
5. 右键通过 IContextMenu / Shell API 拉起系统菜单

这一阶段允许用户同时看到系统桌面图标和我们自绘图标，用于验证交互链路。

验收标准：

- 矩形内图标能画出来
- 双击能打开
- 右键能出菜单
- 拖拽能在矩形内生效

### 阶段 B：托管图标进入“系统隐藏，本应用显示”

目标：

- 消除双份图标
- 让应用真正接管托管图标显示

做法：

1. 给每个被托管图标加 `visibility_mode`
2. 托管后把系统桌面上的对应图标移到隐藏区，或切换为隐藏状态
3. 矩形内仅保留应用自绘版本
4. 重新登录、重启 Explorer 后根据持久化记录重建隐藏/托管状态

验收标准：

- 矩形内只看到一份图标
- 图标操作全部通过应用侧完成
- Explorer 重启后可恢复

### 阶段 C：矩形驱动图标布局，不再驱动桌面布局

这是概念上最重要的一步。

当前逻辑是：

`矩形改变 -> 推动系统桌面图标位置变化`

最终应变成：

`矩形改变 -> 更新应用内托管图标布局`

只有当用户明确要求“退出时恢复到桌面”时，才把布局重新写回系统桌面。

也就是说，Windows 桌面坐标只作为：

- 初始导入来源
- 退出恢复目标

不再作为运行时真源。

### 阶段 D：把未分组区域也纳入应用托管

这是完全摆脱 Windows 桌面的关键最后一步。

如果系统桌面还有大量未托管图标继续显示，就还是双系统并行。

建议最终引入：

`Root Managed Surface`

即整块桌面都由应用托管，只是视觉上分为：

- 已分组矩形区域
- 未分组自由区域

这意味着：

- 全部桌面图标都由应用绘制
- Windows 桌面图标可以整体隐藏
- 矩形分组只是这张托管桌面上的一个功能层

这是最完整、最干净的终态。

## 启动、退出、重启的闭环

### 启动闭环

1. 启动应用
2. 连接 Explorer 和桌面源
3. 读取持久化矩形与托管图标数据
4. 建立 `ManagedDesktopRuntime`
5. 创建自绘桌面承载层
6. 恢复所有矩形
7. 恢复每个矩形内托管图标的位置与顺序
8. 根据策略隐藏系统桌面图标
9. 进入托管运行态

### 退出闭环

退出策略必须配置化，不能只有一种。

建议支持：

#### 模式 1：退出恢复桌面

- 把托管图标坐标写回系统桌面
- 显示系统桌面图标
- 销毁托管层窗口

适合保守模式。

#### 模式 2：退出保留托管状态

- 保存当前托管布局
- 不强制写回分组后的桌面布局
- 下次启动时优先恢复托管层

适合长期使用模式。

#### 模式 3：异常退出恢复保护

为了避免崩溃后图标丢失，必须有兜底：

- 启动时检查上次是否异常退出
- 如果异常退出且系统桌面处于隐藏或半隐藏状态，优先执行恢复
- 恢复完成后再决定是否重新进入托管态

### Explorer 重启闭环

Explorer 重启是这个项目的硬场景，必须单独设计。

建议流程：

1. 监听桌面宿主窗口失效
2. 检测到 Explorer 重建后重新解析桌面句柄
3. 重建桌面源连接
4. 验证托管图标与系统图标的 identity 对应关系
5. 重新应用隐藏/恢复策略
6. 刷新托管层显示

关键点：

- 托管层不能依赖某个固定 `WorkerW`
- 自绘层存在期间，Explorer 重启不应让矩形和图标消失

## 图标交互实现方案

### 1. 双击打开

建议优先使用 Shell 路径或 PIDL 打开，而不是只靠文件路径。

原因：

- 快捷方式
- 特殊文件夹
- 回收站
- 控制面板项

这些并不总能用普通路径表示。

### 2. 系统右键菜单

建议通过 Shell 的 `IContextMenu` 接口拉起真正系统菜单。

这样能最大化保留用户熟悉的桌面行为：

- 打开
- 以管理员身份运行
- 重命名
- 删除
- 发送到
- 属性

如果某类图标暂时拉不起系统菜单，可以降级到应用自己的兼容菜单。

### 3. 图标拖拽

建议分为两类：

#### 矩形内拖拽

- 调整顺序
- 自由布局移动
- 网格吸附

#### 矩形间拖拽

- 从 A 分组拖到 B 分组
- 拖到未分组区
- 拖出分组后自动解除托管

### 4. 框选

最终框选应当由应用自己的图标承载层处理，而不是继续借助桌面原生框选。

### 5. 重命名

推荐由应用触发，实际落到 Shell / 文件系统重命名，再回写显示名。

## 布局系统建议

建议尽早明确支持两种布局模式：

### 模式一：规则网格

优点：

- 简单稳定
- 容易做自动排列
- 容易适配缩放

适合第一版托管。

### 模式二：自由布局

优点：

- 更接近真实桌面
- 用户可自由摆放

缺点：

- 碰撞处理复杂
- 缩放时要定义相对坐标规则

建议策略：

- 第一阶段先只做规则网格
- 数据模型提前兼容自由布局

## 迁移路线

不建议一次性推翻重做，建议按以下顺序推进。

### 第一步：把当前项目定义为“过渡态”

当前版本继续保留：

- 读取桌面图标
- 移动桌面图标
- 绘制矩形
- 单分组编辑

但明确它只是过渡方案，不作为最终形态。

### 第二步：引入自绘图标能力

先在矩形里绘制图标，不急着隐藏系统图标。

目标是先打通：

- 图标渲染
- 双击打开
- 右键菜单
- 矩形内拖拽

### 第三步：切换托管显示权

让被托管图标只在应用层显示，不再依赖系统桌面展示。

### 第四步：矩形驱动布局真源

把运行时坐标真源从“桌面图标坐标”切换成“应用托管数据”。

### 第五步：扩展为全桌面托管

引入未分组区域，彻底摆脱原生桌面显示依赖。

## 风险点

### 1. Shell 菜单与特殊对象支持复杂

普通文件、快捷方式、目录都比较直接，但：

- 回收站
- 此电脑
- 控制面板对象
- UWP 快捷方式

都需要更稳的 PIDL / ShellItem 处理。

### 2. 高 DPI / 多显示器

图标绘制、文字截断、命中区域、拖拽偏移都必须统一使用 DPI 感知坐标。

### 3. Explorer 生命周期

应用既然想接管桌面体验，就不能在 Explorer 重启时一起失效。

### 4. 性能

图标数量较多时，自绘缓存、局部重绘、图标位图缓存都要做。

### 5. 数据恢复安全

异常退出时，如果系统桌面图标已隐藏，恢复逻辑一定要有兜底，否则用户会误以为图标丢失。

## 验收标准

当以下条件都满足时，可以认为“矩形功能对接桌面图标实现”完成：

1. 矩形内图标由应用自己绘制，不再依赖 Windows 桌面绘制。
2. 被托管图标不会和系统桌面图标重复显示。
3. 用户可在矩形内完成双击、右键、拖拽、重命名等核心操作。
4. 矩形移动、缩放时，图标布局由应用运行时直接更新。
5. 重启应用后，所有矩形和图标托管关系都能恢复。
6. Explorer 重启后，托管层能自动重连并恢复。
7. 退出恢复策略可配置，且异常退出有保护路径。
8. 未分组图标最终也能纳入应用托管，形成完整闭环。

## 推荐实施拆分

建议按以下阶段立项，而不是一次压满：

### 14-1 自绘图标原型

- 在矩形内绘制应用自有图标
- 打通双击打开
- 打通右键菜单

### 14-2 托管图标运行时

- 引入 `ManagedIconInstance`
- 运行时改为以应用数据为真源

### 14-3 托管显示切换

- 被托管图标切换为应用显示
- 系统桌面图标进入隐藏策略

### 14-4 矩形驱动布局

- 移动矩形
- 缩放矩形
- 图标重排
- 矩形间拖拽

### 14-5 启停与异常恢复闭环

- 启动恢复
- 退出恢复
- Explorer 重启恢复
- 异常退出保护

### 14-6 全桌面托管

- 未分组区域纳入托管
- 完整摆脱 Windows 原生桌面显示依赖

## 结论

如果目标只是“让矩形看起来在图标下面”，继续调窗口层级还可以勉强往前走一段。

但如果目标是：

- 真正让矩形托举图标
- 真正把分组变成自己的桌面容器
- 真正收敛拖拽、缩放、恢复、重启、右键这些问题

那就必须把方案升级为：

`以应用自绘图标层为核心，以 Windows 桌面为数据源和系统能力桥接，而不是继续把 Windows 桌面当最终界面`

这才是后续多分组、设置管理、视觉增强、快照、跨重启恢复能够长期稳定演进的底座。
